## 压缩的核心原理：有损压缩 vs 无损压缩 {#theory}

理解数字图像压缩首先必须区分两种截然不同的技术路线：

| 对比维度 | 有损压缩（Lossy Compression） | 无损压缩（Lossless Compression） |
| :--- | :--- | :--- |
| **数学本质** | 丢弃人眼不易察觉的高频细节与微小色差，**数据不可完全复原** | 利用统计学冗余（如哈夫曼编码、LZ77/Deflate），**数据可 100% 完美复原** |
| **典型格式** | JPEG、WebP (有损模式)、AVIF、HEIC | PNG、GIF、WebP (无损模式)、TIFF |
| **压缩比率** | 极高（通常可达 **60%～90%** 缩减） | 中等偏低（通常仅能缩减 **15%～40%**） |
| **多次保存影响** | 产生「世代损失（Generation Loss）」，每重编码一次画质劣化一次 | 无论重新保存多少次，像素矩阵与校验和保持绝对一致 |
| **最佳应用对象** | 摄影照片、复杂写实插画、色彩层次丰富渐变的写实场景 | 界面图标、Logo、线框图、带 Alpha 透明通道的 UI 素材、像素画 |

### 1. 人类视觉系统（HVS）的生理特性
人眼视网膜对**亮度（Luminance, Y）**的微小变化极度敏感，但对**色度（Chrominance, Cb/Cr）**的细微偏差感知力较弱。
此外，人眼对画面中平滑均匀区域的平缓变化非常敏感，而对高密度的微小噪点、复杂树叶纹理等高频信息的局部丢失具有天然的感知容忍度。现代有损压缩标准正是建立在这一生理学基础之上。

### 2. JPEG 与 WebP 的数学变换流程
以最经典的 JPEG/WebP 为例，整个压缩流水线分为四个核心环节：
```
[原始 RGB 像素矩阵] 
      │
      ▼ (色彩空间转换)
[YCbCr 色彩模型 + 色度抽样 (4:2:0)]
      │
      ▼ (划分为 8x8 像素宏块)
[离散余弦变换 (DCT / Discrete Cosine Transform)]
      │ (将空间域像素转换为频域能量系数)
      ▼
[非线性量化 (Quantization)]  <── 画质滑块质量系数 (Quality 0.0 - 1.0) 作用于此
      │ (高频系数除以量化步长并舍入，产生大量零值)
      ▼
[熵编码 (Entropy Coding: 锯齿扫描 + 游程编码 + 霍夫曼编码)]
      │
      ▼
[极致紧凑的最终压缩文件]
```
在 WebUtils 图片压缩工具中，控制面板上的「压缩质量滑块（Quality: 0.1 ~ 1.0）」本质上就是在动态调节**频域量化矩阵的步长系数**。数值越大，量化步长越小，保留的频域细节越丰富；数值调低时，量化步长增大，大量高频分量被归零，从而释放出惊人的文件体积缩减空间。

## 主流格式压缩特性与适用场景全景 {#formats}

不同图像格式在面对不同图像内容时，压缩效率表现差异巨大。盲目用单一格式压所有图片，往往会造成严重的体积浪费或画面污损。

### 1. JPEG / JPG 格式
- **技术优势**：兼容性极佳，全球所有设备、系统、浏览器与邮件客户端 100% 支持；对于自然风景、人物肖像等复杂写实内容压缩比非常优秀。
- **技术缺陷**：完全不支持透明通道（Alpha）；对文字截屏、纯色线框图等高对比硬边缘内容极不友好，极易在文字边缘产生类似蚊蝇飞舞的「振铃伪影（Ringing Artifacts）」。
- **压缩建议**：质量因子建议设置在 **0.75 ~ 0.85** 之间。在此区间内，文件体积通常只有未压缩位图的 10%~20%，而人眼在正常视距下几乎无法辨别任何噪点。

### 2. PNG 格式
- **技术优势**：真正的像素级无损保证，完美支持 8 位到 32 位的完整 Alpha 渐变透明度；对于锐利边缘、纯平色彩、图表图标的压缩效率极高。
- **技术缺陷**：用于风景与摄影实景图时体积极其臃肿；无损压缩的运算复杂度高。
- **压缩建议**：如果不需要透明背景，绝不要将摄影大图保存为 PNG；如果必须使用 PNG，可尝试色板量化（Color Quantization），将 24 位真彩色降阶为 256 色的 PNG-8。

### 3. WebP 格式（推荐的首选现代格式）
- **技术优势**：Google 推出的现代网络图像标准，同时支持**有损**与**无损**两种压缩模式，并且在两种模式下均完整支持 Alpha 透明通道。在相同视觉质量下，WebP 有损文件比同画质 JPEG **体积小 25%～34%**；WebP 无损文件比 PNG **小 26% 左右**。
- **兼容性现状**：截至 2026 年，现代浏览器（Chrome、Edge、Safari、Firefox、各手机端 WebView）支持率已超过 **98.5%**，是构建高性能网站与移动端应用的事实标准首选。

## 常见压缩事故与避坑对照表 {#errors}

在日常工程实践与设计交付中，不恰当的压缩参数常常带来灾难性的视觉损坏。下表整理了高频错误原因及应对指南：

| 异常表现 | 根本原因机制 | 产生后果与危害 | 科学解决思路 |
| :--- | :--- | :--- | :--- |
| **渐变天空出现一圈圈等高线（色带断层）** | 色度量化过度，平滑色阶丢失，产生「Color Banding」伪影 | 视觉质感粗糙，画面显得廉价劣质 | 将压缩质量提升至 0.85 以上，或在导出时引入极其微量的抖动（Dither）噪点抵消断层 |
| **文字或线条周围出现密集脏斑块** | 对高对比硬边缘强行施加 JPEG 高频离散余弦量化截断（振铃效应） | 文本阅读疲劳，截图中的文字边缘模糊发毛 | 截图、线框图与文本图严禁使用有损 JPEG，切换为 PNG 或无损 WebP |
| **压缩后的图片文件体积反而变大** | 针对本来就已经高度压缩的 JPEG 重新编码，或误转为未优化的 PNG | 白白消耗算力，不仅画质变差体积还增加 | 对已经是极致小体积的文件无需重复二压；有损格式不要反向转为 PNG |
| **人物皮肤细节被大面积涂抹抹平** | 过度激进的降噪预滤波或压缩质量低于 0.50 | 皮肤纹理丧失，呈现塑料人偶般的假面感 | 保持质量在 0.75 以上，避免在预处理环节施加过度模糊滤镜 |
| **图片在移动端 Retina 高清屏上显得发虚** | 只顾降低文件体积，盲目缩减了物理像素宽高 | 在 3x 高 PPI 视网膜屏幕上放大显示时像素不足 | 保持高物理像素（例如 2 倍图），但使用较低质量因子（如 0.70），比「低分辨率高画质」清晰得多 |
| **多通道医学/工程图颜色发生漂移** | 压缩过程中误丢弃了内嵌的 ICC Color Profile 色彩配置文件 | 在不同广色域（Display P3 / sRGB）屏幕上色彩不一致 | 导出时保留关键色彩元数据，或者在压缩前统一在内存中转换为标准 sRGB 色彩空间 |

## 常见问题解答（FAQ） {#faq}

### Q1：在线压缩图片会降低分辨率（像素尺寸）吗？
**不会。** 纯粹的「压缩（Compression）」只改变每个像素的位深度与编码精度，画面的物理分辨率（宽与高，例如 `1920 × 1080`）保持绝对不变。如果你希望改变宽高的像素数值，请使用配套的 [图片尺寸调整](/tools/media/image-resize) 工具。

### Q2：为什么有些图片反复压缩几次之后，体积不再变化甚至变大？
这是因为每种压缩算法都有其理论上的信息熵极限。当一张图片在第一次压缩时，高频冗余已被完全剔除。再次对已压缩的 JPEG 文件施加有损压缩，算法不但无法发现新的冗余信息，反而会因为离散余弦变换舍入误差引入新的杂色噪点，迫使编码器分配额外的二进制位来记录这些伪影，导致文件体积不降反升。因此，**强烈建议始终使用最初始的高清原图进行单次压缩**。

### Q3：压缩质量滑块拉到 1.0（100%）代表无损吗？
**在 JPEG 格式下，100% 质量并不等于数学上的无损。** JPEG 的 100% 质量只是采用了全部由 1 组成的极细量化表，它最大程度地保留了频域系数，但空间转换与舍入过程中依然存在微小的精度损失。如果你需要真正的 100% 数学无损，必须选择 PNG 格式或者将 WebP 切换为无损编码模式。

### Q4：在你们网站上传高保密性的商业设计稿安全吗？
**绝对安全。** WebUtils 的压缩算法完全运行在您的本地浏览器进程沙盒内部。工具调用的是浏览器的内建底层 API 进行二进制流解码与重新编码，数据从未离开过您的设备内存。你可以直接在断开 Wi-Fi 的飞行模式下测试本工具，所有功能均完全正常运作。

### Q5：手机端拍的照片为什么压缩后偏色了？
现代高端智能手机（如 iPhone）默认采用广色域（Display P3）并内嵌高动态范围（HDR）增益图层。而部分老旧平台或普通显示器仅支持标准 sRGB 色彩空间。在有损压缩重新编码时，如果浏览器将 P3 色彩矩阵强制映射为 sRGB 且未做色彩补偿，就会导致原本鲜艳的红色或绿色显得暗淡泛灰。WebUtils 已针对现代广色域环境进行了针对性校准，最大程度保证跨端色彩还原一致性。
