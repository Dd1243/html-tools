## 核心一句话 {#tldr}

**文本对比的核心目标是以最小的编辑距离（Edit Distance）还原两段文本之间的变迁轨迹。** 无论是发现一行代码中被悄悄修改的变量名，还是排查法务合同中增加的关键除外责任条款，选择正确的对比粒度（字符级 vs 行级）并学会合理过滤无关空白干扰，是实现精准比对的前提。

主工具：[在线文本对比工具](/tools/text/text-diff)。若主要面对结构化编程语言并需要语法高亮，请使用 [代码 Diff 对比工具](/tools/dev/code-diff)；若仅需要简易的双栏对齐比对，请前往 [文本比较工具](/tools/text/text-compare)。

## 认识 Diff：从最长公共子序列到 Myers 算法 {#algorithms}

计算机究竟是如何在成千上万行的文本中，智能计算出哪些行被增加、哪些行被删除的？这依赖于经典算法理论的演进：

| 算法机制 | 核心思想与时间复杂度 | 优势与特长 | 典型局限与缺陷 |
| :--- | :--- | :--- | :--- |
| **最长公共子序列（LCS）** | 基于动态规划求两序列的最长公共子序列，复杂度 $O(N \times M)$ | 逻辑直观、易于实现，对极短文本效果极佳 | 内存消耗极大，在万行长文件比对时容易遭遇超时崩溃 |
| **Myers 差异算法（现代工业标配）** | 将 Diff 问题转化为网格图搜索中的最短路径（Shortest Edit Path）搜索，复杂度 $O(N \times D)$（$D$ 为差异步数） | **在变动较小（$D \ll N$）的高频场景下速度极快**，Git 默认原生算法 | 当两份文件毫无重合度（$D \approx N$）时退化为平方级耗时 |
| **Patience Diff（耐心算法）** | 优先匹配全局唯一且出现频次均为 1 的「锚点行」，再递归切分比对 | 完美解决函数大面积重排带来的乱序伪差异 | 计算复杂度稍高，对于只有微小修改的代码段优势不明显 |
| **Histogram Diff（直方图算法）** | 统计行词频直方图寻找低频主干行切分 | 大规模重构代码合并时比 Myers 更符合人类直觉 | 算法实现复杂，对无序长文本适应性一般 |

### Myers 算法在网格图中的形象漫步
Myers 算法之所以能成为 Git 与现代编辑器的首选，是因为其精妙的几何转化：
- 设原文 $A$ 有 $N$ 个字符，新文 $B$ 有 $M$ 个字符，构成一个从坐标 $(0,0)$ 到 $(N,M)$ 的矩形网格；
- **向右走一步**：代表在原文字符处执行**删除（Delete）**操作；
- **向下走一步**：代表在新文字符处执行**插入（Insert）**操作；
- **沿对角线向右下斜走**：代表两个字符完全相同，**无需任何编辑代价（Cost = 0）**！
Myers 算法的核心就是使用广度优先搜索（BFS）以极高效率寻找一条**消耗最少水平和垂直步数、尽可能多走对角线的最优路径**。最终走过的水平红线即为被删除行，垂直绿线即为新增行。

## 对比粒度全景：字符级、单词级与行级对比 {#granularity}

在实际使用对比工具时，选择正确的比对粒度直接决定了排障效率：

### 1. 行级对比（Line-by-Line Diff）
- **判定标准**：以换行符 `\n` 为绝对分割界限，只要整行中有一个标点不同，整行均被标记为变更。
- **最佳应用场景**：代码审查（Git Commit Diff）、大型日志对比、结构化数据清单核对。
- **不足之处**：如果一行文本非常长（例如一段 500 字的段落），仅仅修改了一个逗号，行级对比会将整段 500 字全部标为红色删除加绿色新增，用户无法一眼看出究竟改了哪几个字。

### 2. 字符级对比（Character-by-Character Diff）
- **判定标准**：深入到每一行内部，将每一个 Unicode 字符单独作为比较单元。
- **最佳应用场景**：法务合同条款修改、论文修改排查、微小代码变量名纠错（如把 `user_name` 改为 `username`）。
- **不足之处**：计算量极大；在整段结构发生颠覆性重构时，字符级比对可能会产生极其琐碎零散的交错高亮，反而破坏人类阅读的连贯性。

### 3. 单词级对比（Word-by-Word Diff）
- **判定标准**：以西文单词（空格/标点切分）或中文双字词作为语义切分单元。
- **最佳应用场景**：英文文章校对、学术论文同行评审（Peer Review）修改稿对照。

## 文本对比工具实操操作全流程 {#steps}

利用 WebUtils 在线文本对比工具进行精准审查的标准操作指引：

1. **导入左右两侧对比内容**：
   - 打开 [在线文本对比工具](/tools/text/text-diff)；
   - 在左侧输入面板粘贴「原始版本（Original / 旧版本）」文本；
   - 在右侧输入面板粘贴「修改版本（Modified / 新版本）」文本；
   - 支持直接从本地拖拽或导入两个 `.txt`、`.md` 或 `.json` 文件。
2. **选择适合的视图模式**：
   - **分屏并排模式（Side-by-Side Split View）**：左栏显示原版，右栏显示新版。左右两栏垂直滚动条完全同步联动。这是排查长文本修改最直观舒适的排版模式；
   - **内联统一模式（Unified Inline View）**：将变动合并在一个单列窗口中展示，以 `-` 红色标识删除行，以 `+` 绿色标识增加行（与命令行 `git diff` 输出格式高度一致）。
3. **启用智能过滤配置选项**：
   - **忽略空白字符（Ignore Whitespace）**：极其重要的实用开关！勾选后，工具将自动忽略行首缩进空格、Tab 与空格混用、以及行尾多余空格的差异，仅聚焦在实质性文字修改上；
   - **忽略大小写（Ignore Case）**：用于排查纯文本内容而不关心英文大小写微调的特定场景；
   - **开启内联字符级高亮（Inline Diff）**：在标明变动行的同时，用加深背景色精确圈出被修改的具体几个字符。
4. **定位与导出变更差异报告**：
   - 点击导航栏上的「上一个差异（Prev）」/「下一个差异（Next）」快捷按钮，可以在数百行文本中瞬间穿梭定位关键改动点；
   - 确认核对完毕后，可点击「复制纯差异补丁」或「一键导出对比报告」保存审查记录。

## 常见 Diff 翻车事故与避坑对照表 {#errors}

| 异常现象 / 误报症状 | 底层技术诱因机制 | 产生的困扰与危害 | 正确化解与避坑建议 |
| :--- | :--- | :--- | :--- |
| **整份文件每一行都被标记为修改** | Windows 系统 CRLF（`\r\n`）与 Linux/Mac 系统 LF（`\n`）行尾换行符混淆 | Git 提交产生虚假全量变更，历史记录被严重污染 | 开启「忽略行尾换行符差异」开关，或在编辑器中统一配置为 LF 换行 |
| **Tab 制表符与空格混用引发大面积红绿跳动** | 团队协作中有人使用 4 个空格缩进，有人使用 1 个 Tab 缩进 | 视觉对齐但实际底层二进制不一致，Diff 噪音极多 | 在对比工具中开启「忽略空白缩进（Ignore Whitespace）」，屏蔽无意义格式干扰 |
| **大段文字被错位对齐，产生错误的对应关系** | 两个段落开头恰好包含了相同的「第 X 条」或「function」等通用高频词 | 算法贪婪地将两个不相关的段落连接对齐，导致后续排版彻底混乱 | 尝试在段落之间补充唯一性的空行隔离，或切换为耐心算法（Patience Diff）模式 |
| **中文字符比对出现奇怪的乱码断片** | 早期比对逻辑按字节（Byte）而非 Unicode 字符切分，把 UTF-8 的 3 字节汉字切断 | 汉字显示为乱码方块 `\uFFFD`，对比彻底失效 | WebUtils 采用纯原生 Unicode 字符串索引，100% 杜绝多字节截断乱码 |
| **长行文本（Single-line Minified）页面卡死** | 压缩后的 JSON 或 JS 只有 1 行长达数兆字符，触发了字符级对比的最坏复杂度 | 浏览器主线程算力耗尽，页面无响应卡死 | 先使用 [JSON 格式化工具](/tools/dev/json-formatter) 将两份文本各自美化换行后，再执行文本比对 |

## 典型业务场景比对实战范式 {#scenarios}

### 场景一：法务商务合同审阅与条款红线排查
- **痛点**：供应商回传了一份经过对方律师修改的采购框架合同，虽然对方声称「只是修改了几个错别字」，但必须确保核心违约金、付款周期与知识产权归属条款没有被暗中篡改。
- **最佳实战**：
  1. 将我方最初发出的标准模板粘贴在左栏，对方盖章回传的修改草稿粘贴在右栏；
  2. 启用**「分屏双栏视图」**并开启**「字符级差异高亮」**；
  3. 点击「下一个差异」逐一过目：系统瞬间高亮圈出「不可抗力条款中被删除了“流行病爆发”五个字」、「付款账期由 30 天被悄悄改为了 90 天」；
  4. 截取对比证据图或直接导出变更清单，作为商务谈判的有力抓手。

### 场景二：生产环境微服务配置文件（YAML / Nginx）变更审查
- **痛点**：线上服务突然报错 502，运维人员需要紧急比对当前线上集群运行的 `nginx.conf` 与昨天备份的健康配置到底有何不同。
- **最佳实战**：
  1. 将健康备份与故障配置分别贴入左、右栏；
  2. 勾选**「忽略首尾空白符」**（剔除因为运维人员打回车引起的格式变动）；
  3. 瞬间锁定核心差异行：`proxy_read_timeout 60s;` 被误配置成了 `proxy_read_timeout 6s;`！故障排查时间从半小时缩短到 10 秒钟。

## 常见问题解答（FAQ） {#faq}

### Q1：在你们网站粘贴企业商业合同或敏感源代码会不会泄露？
**绝对不可能泄露。** WebUtils 的所有文本对比算法全部基于浏览器端本地 JavaScript 引擎实时运算。用户键入或导入的两份文本数据，在整个比对生命周期内**完全保存在您本机浏览器的运行时内存中**，绝不会产生任何上传到远程云服务器的 HTTP 请求。断开网络连接离线使用，全部比对与高亮功能完全正常。

### Q2：为什么有时候只改了一个字，整个段落都被标红删除了？
这是因为您当前处于纯粹的**「行级对比模式」**。在行级模式下，整行文本被作为一个不可分割的最小比较原子。请在工具顶部控制面板中勾选**「开启行内字符级高亮（Inline Diff）」**，工具便会进一步在该行内部启动二次微观对比，仅将发生改变的那一个字用深色背景精确圈出。

### Q3：两段文本的段落顺序完全颠倒了，对比工具能识别出来是“被移动了”吗？
经典的 Myers 算法是**线性单向求解算法**，它只能识别出「上面一段被删除了，下面增加了一段新内容」，通常不会智能标记为“整段位置下移”。如果您需要专门跟踪大段函数或模块的跨行迁移，建议关注专门的语义重构分析工具，或结合两侧关键词搜索进行交叉验证。

### Q4：最大支持对比多大的文本文件？
WebUtils 算法经过了虚拟滚动（Virtual Scroll）与增量切片优化。通常两份 **10,000 行以内**的常规代码文件或小说文本（数百 KB 级别），在现代主流电脑浏览器中都能实现即时秒开。如果单份文件超过 50,000 行或体积达到数十 MB，由于 DOM 树高亮节点的渲染开销巨大，建议分章节或分模块拆开进行精细化对比。

### Q5：如何把对比结果分享给没有安装专业 Diff 软件的同事？
点击工具操作栏中的「导出 HTML 审查报告」按钮，系统将把带颜色高亮、双栏并排对齐的当前视图打包为一个独立的本地单文件 HTML。你可以将这个 HTML 直接通过微信或邮件发送给法务或业务同事，对方双击浏览器即可打开查看，完全不需要安装任何专业代码编辑器。
