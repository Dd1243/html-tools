1. 全半角标点混排：为什么 Word 粘贴后总「乱」

如果你曾经把一份 Word 文档的内容复制粘贴到网页编辑器、微信公众号后台或者任何 CMS 系统中，大概率遇到过这样的噩梦：逗号一会儿是半角的 , 一会儿是全角的，，句号在 . 和 。 之间随意跳动，引号变成了看不懂的弯弯曲曲的""''，好好的一篇稿子被标点符号糟蹋得面目全非。你一个一个字符去改，改到眼睛发酸，改到怀疑人生——为什么只是复制粘贴一下，标点就会「乱」成这样？

答案藏在三层历史遗留问题里。第一层是编码的历史割裂。中文标点最早收录在 GB2312（1980）和后来的 GBK、GB18030 编码中，每个字符占两个字节，俗称「全角」；而英文标点沿用 ASCII 编码，每个字符只占一个字节，俗称「半角」。两套编码里的标点虽然视觉上相似，却有完全不同的码位。到了 Unicode 时代，两套字符被同时收录，于是同一个「逗号」在 Unicode 里就同时存在了半角（U+002C）和全角（U+FF0C）两种合法表示。这给了软件「自由发挥」的空间。

第二层是 Office 的智能引号机制。微软 Word 有一个叫做「智能引号」（Smart Quotes）的功能，当你在文档中敲下一个直引号 " 时，Word 会自动把它替换成左右有方向的弯引号（左双引号 " U+201C、右双引号 " U+201D、左单引号 ' U+2018、右单引号 ' U+2019），让排版更接近出版级效果。问题是，一旦这些弯引号离开了 Word 的排版环境，被粘贴到纯文本编辑器、网页输入框或其他不支持弯引号的场景，它们的显示就会出问题——有的系统把它们渲染成乱码，有的干脆替换成了问号或方框。更棘手的是，Word 粘贴内容时，还会根据目标环境的「猜测」自动在全角和半角之间做一些「智能转换」，其结果通常是一段文本里同时出现两到三种编码的同类标点。

第三层是跨平台剪贴板的字符标准化缺失。Windows 的剪贴板、macOS 的粘贴板、Linux 的剪贴板管理器，以及各种远程桌面、云笔记、即时通讯软件的粘贴转发机制，对于 Unicode 字符的处理方式并不统一。一个弯引号从 Windows Word 复制到 Mac Pages 再转发到浏览器里，可能已经经历了三到四次内部转换，出现全半角混排、引号方向丢失的情况几乎是必然的。

理解了这些根由，我们也就明白了：标点符号的混乱，本质上不是用户「打错了字」，而是不同软件、不同编码、不同平台之间的历史积弊在文本中留下的痕迹。既然这些积弊短期内不会消失，我们就需要一个专门的工具，对复制粘贴后的文本做一次彻底的标点标准化——这正是本工具的设计初衷。

GB2312 与 ASCII 的编码错位

从码位上看，半角 ASCII 标点集中在 U+0020 到 U+007E 范围内，而对应的中文全角标点被 Unicode 安排在了 U+FF01 到 U+FF60 的「半角及全角形式」区块。也就是说，U+FF01（！）= U+0021（!）+ 0xFEE0，U+FF0C（，）= U+002C（,）+ 0xFEE0，以此类推。这种偏移关系给我们提供了一个非常方便的转换思路：只要判断字符在某个范围内，做简单的加减就可以完成全半角互转。本工具的核心转换正是基于这个原理实现的。

2. 中文排版标点规范速查（GB/T 15834-2011）

中华人民共和国国家标准《标点符号用法》（GB/T 15834-2011）是中文标点的权威依据。不管你是写论文、做公众号、出产品文案，只要使用的是简体中文，就应该遵循这一标准。下面我们把常用的核心条目速查整理出来，方便随时对照。

句末点号

  • 句号（。）：用于陈述句末尾，占一个汉字位置，居左下。
  • 问号（？）：用于疑问句末尾。反问句末尾一般也用问号。
  • 叹号（！）：用于感叹句末尾。强烈的祈使句、反问句也可用。

句内点号

  • 逗号（，）：句子内部的一般性停顿。
  • 顿号（、）：句子内部并列词语之间的停顿。注意：并列的英文单词、阿拉伯数字之间宜用逗号而非顿号。
  • 分号（；）：复句内部并列分句之间的停顿。
  • 冒号（：）：提起下文或总结上文。

标号（核心 9 类）

  1. 引号（「」『』）：外层用「」，内层用『』。引文末的点号位置：独立成段的引文放在引号内，不成段的放在引号外。
  2. 括号（（ ）［ ］〔 〕）：行文中注释性的文字。
  3. 破折号（——）：占两个汉字位置，即两个「—」连排（实际排版中常统一为一个 em-dash —）。
  4. 省略号（……）：占两个汉字位置，即两个「…」连排。注意不要用六个英文点 ......。
  5. 书名号（《》〈〉）：书名、篇名、报纸名、刊物名等。外层《》，内层〈〉。
  6. 着重号（．）：标在字下，标示强调。
  7. 连接号（— ～ -）：表示时间、地点、数目等的起止。
  8. 间隔号（·）：外国人名、书名与篇名之间的间隔。
  9. 专名号（____）：古籍或文史作品中的人名、地名、朝代名等。

实际工作中，最常出错的是引号嵌套（外层用了『』内层用了「」，顺序颠倒）、省略号用六个英文点、破折号用两个减号代替——这些都是本工具自动修正的重点目标。

4. 「弯引号」与「直角引号」：出版级排版的取舍

关于引号的争论，在中文排版圈里已经持续了很多年。核心的分歧集中在两个问题上：第一，中文排版到底应该用弯引号（""''）还是直角引号（「」『』）？第二，如果用直角引号，嵌套时谁在外谁在内？

弯引号 vs 直角引号的文化差异

弯引号（Curly Quotes / Smart Quotes）源自英文活字印刷传统。英文的引号分左右：左双引号 "（U+201C）像两个反写的 6，右双引号 "（U+201D）像两个正写的 9；单引号同理是 '（U+2018）和 '（U+2019）。它们是英文出版界的绝对主流，几乎所有英文书籍、杂志、网站都默认使用弯引号。

直角引号（Corner Brackets / CJK Quotation Marks）则源自中文古籍的批注传统。「」（U+300C/U+300D）和『』（U+300E/U+300F）最早是中文圈（包括中国大陆、台湾、香港、日本、韩国）共同的排版习惯。但中国大陆在 1950 年代的文字改革中，一度推动弯引号的普及，原因是打字机上更容易输入；改革开放后又因为 Windows 简体中文版和 Word 的默认设置，弯引号在文档处理领域成了事实上的标准。直到 2011 年新版 GB/T 15834 明确了「」『』的规范地位，直角引号才在出版物和严谨写作中回归。

目前的格局是：学术出版、正式公文、报社期刊的编辑部一般遵循 GB/T 15834，使用直角引号；而普通用户、办公文档、网页博客因为系统默认，仍大量使用弯引号。两种选择都不算「错」，问题在于同一篇文稿里二者不能混用——本工具的「弯引号→直角引号」选项，就是帮你把整篇文稿里零散的弯引号统一替换为规范的直角引号，并自动处理嵌套关系。

引号嵌套的地区差异

中国大陆 GB/T 15834-2011 明确规定：引号分层使用时，外层用双引号（即「」），内层用单引号（即『』）。示例：他说：「我常读《论语》，其中『学而时习之』一句尤其发人深省。」

台湾、香港的繁体出版习惯则有所不同：他们的「双引号」是「「」」（两个「「在外，两个」」在内，或称双直角），单引号是『』，嵌套时外层用「「」」，内层用『』。日本排版则习惯外层用「」，内层用『』，与中国大陆相同，但竖排时位置会镜像到左下角。

如果你需要面向繁体中文用户，把工具源码中的引号映射表稍作调整即可，核心逻辑保持不变。

代码注释里为什么必须关弯引号

这条给写代码的朋友：千万不要在代码文件（.js .py .go .java .cpp 等等）的注释里用弯引号，更不要让弯引号出现在字符串字面量中。因为编译器和解释器只识别半角直引号 " 和 '，遇到弯引号要么报语法错误，要么在运行时产生极难排查的 Bug。Word 的智能引号功能是代码文件的天敌，建议任何涉及代码的文档工作一律关闭该功能（Word → 选项 → 校对 → 自动更正选项 → 键入时自动套用格式 → 取消勾选「直引号替换为弯引号」）。

5. 常见 9 种标点错误 + 真实纠错案例

下面列举的 9 种错误，是我们从上千份真实文稿中归纳出的高频问题。每一种都附有「错误示例→正确写法」的对照，你可以直接用本工具粘贴错误示例，验证校正结果是否符合预期。

错误 1：中英文逗号错用

错误：今天天气很好,我打算出去散步,顺便买杯咖啡。 正确：今天天气很好，我打算出去散步，顺便买杯咖啡。

分析：中文句子内部的逗号必须用全角「，」。半角逗号只应用于英文句子或代码中。

错误 2：英文句子里误用中文句号

错误：The quick brown fox jumps over the lazy dog。 正确：The quick brown fox jumps over the lazy dog.

分析：英文句子的末尾必须用半角「.」。工具的「英文标点标准」模式会自动处理这种情况。

错误 3：引号嵌套顺序颠倒

错误：他说：『我最近在看「三体」，非常精彩。』 正确：他说：「我最近在看《三体》，其中『古筝行动』那段尤其震撼。」

分析：外层必须是「」，内层必须是『』。另外注意作品名用书名号《》而非引号。

错误 4：省略号用六个英文点

错误：她沉默了许久......终于开口说了话。 正确：她沉默了许久……终于开口说了话。

分析：中文省略号是两个「…」（U+2026）连排，共占两个汉字宽度，不是六个英文点。

错误 5：破折号用两个减号

错误：人生最大的敌人--不是别人，而是自己。 正确：人生最大的敌人——不是别人，而是自己。

分析：标准破折号是「——」（两个 em-dash 或一个双宽度字符），不要用两个半角减号「--」代替。

错误 6：书名号和引号混用

错误：我最喜欢的歌曲是"晴天"，收录于"叶惠美"专辑。 正确：我最喜欢的歌曲是《晴天》，收录于《叶惠美》专辑。

分析：歌曲名、专辑名、电影名、书名等作品名一律用书名号《》。引号用于引述说话内容、短词语或成语。

错误 7：顿号用在英文数字之间

错误：本次考试前 3 名是 1、李华、2、王芳、3、赵强。 正确：本次考试前 3 名是：1. 李华，2. 王芳，3. 赵强。

分析：阿拉伯数字之间的并列分隔，规范做法是加英文点号（1. 2. 3.）后用中文逗号分隔，而不是顿号。纯中文词语并列时才能用顿号。

错误 8：连续多个感叹号或问号

错误：这件事真的太让人生气了！！！！你到底有没有在听我说话？？？？ 正确：这件事真的太让人生气了！你到底有没有在听我说话？

分析：规范中文排版中，句末只允许出现一个感叹号或一个问号。表达强烈语气可借助副词和上下文，不靠堆叠标点。

错误 9：冒号后直接引句号嵌套错误

错误：老师说："同学们要记住三条。第一、早睡早起。第二、按时交作业。第三、上课认真听讲。"。 正确：老师说：「同学们要记住三条：第一，早睡早起；第二，按时交作业；第三，上课认真听讲。」

分析：引号外面再多加一个句号属于典型错误。内部列举条目用逗号和分号分层，不用顿号。

6. 工具使用详解：3 个场景一键修稿

下面用三个真实工作场景，演示如何组合使用本工具的模式切换和复选框选项，最高效地完成标点校正工作。

场景 A：论文 Word → 网页复制后整段标点错乱

背景：你花了三个月写的毕业论文完成了，导师让你把摘要放到学院网站上。你从 Word 里复制粘贴，结果整个段落里逗号句号一半全角一半半角，引号全部变成了弯引号，破折号是两个减号，省略号是六个点。

推荐操作：

  1. 打开标点校正器，模式选择「中文标点标准（默认）」。
  2. 三个复选框全部勾选：弯引号→直角引号、省略号/破折号标准化、删除零宽字符。
  3. 把 Word 里的整段摘要粘贴到左侧输入框。
  4. 点击「一键校正」，一秒内得到标准化结果。
  5. 对照原文快速扫一眼，确认公式或数字编号中的半角标点没有被误伤后，点「复制结果」粘贴到网站后台。

场景 B：多语言产品文案翻译后引号/顿号/书名号不统一

背景：公司产品要做中文化，海外团队给的英文文案经过 4 位翻译接力处理后，中文稿件里有的人用弯引号、有的人用直角引号、有的人用直引号；产品名、功能名有的加书名号、有的加引号、有的什么都不加。

推荐操作：

  1. 先把翻译稿按段落分批粘贴（每批 2000 字以内方便校对）。
  2. 模式选「中文标点标准」，勾选「弯引号→直角引号」和「省略号/破折号标准化」。
  3. 点击「一键校正」后，先复制结果，再用「下载 .txt」把每批结果保存为中间稿。
  4. 对于产品名是否用书名号的问题，工具不会自动添加（因为它无法判断某个词是不是产品名），需要你手动统一。但工具至少把其他标点全部统一了，你只需要集中处理书名号这一件事。

场景 C：旧版 PDF OCR 后产生大量零宽字符和半角中文标点混合

背景：你手头有一份 2008 年扫描的 PDF 旧文档，用 OCR 软件识别后得到的文本里夹杂着大量不可见的零宽字符（U+200B U+FEFF 等），而且因为旧扫描仪的识别误差，中文标点十有七八被识别成了半角英文标点。

推荐操作：

  1. 模式选「中文标点标准」。
  2. 重点勾选「删除零宽字符」和「省略号/破折号标准化」，引号选项根据是否有引号内容酌情勾选。
  3. 先粘贴一小段（约 500 字）做测试，点击校正后观察结果，确认没有把原本正确的地方改坏。
  4. 测试通过后，把整份 OCR 文本分批粘贴处理，最后用「下载 .txt」功能合并保存。
  5. 处理完毕后建议再做一次 OCR 置信度校验：把工具修正的结果与 PDF 原图对照，尤其是数字和专有名词部分，因为零宽字符有时会与 OCR 的断词错误交织在一起。

7. 进阶：正则 + JS 自定义扩展

本工具的核心逻辑全部是用纯 JavaScript + 正则表达式（RegExp）实现的，没有引入任何第三方库。这意味着你可以非常方便地在浏览器的 F12 开发者控制台中扩展它，或者把它的核心规则抠出来用到自己的项目里。

在 F12 控制台自定义 replace 规则

打开本工具页面后，按 F12 打开开发者工具，切换到 Console 控制台。你可以直接访问工具的核心函数 fixPunctuation(text, options)，给它传不同的参数做测试，或者在它执行前后追加自己的 replace 逻辑。

比如你想把文稿里所有的「！！！」改成一个「！」再加上 HTML 标签（仅控制台预览用），可以这样写：

const input = document.getElementById('input').value; let result = fixPunctuation(input, { mode: 'zh', fixQuotes: true, fixEllipsis: true, removeZeroWidth: true }); result = result.replace(/！{2,}/g, '！'); console.log('自定义修正后的结果：', result);

本工具源码中的核心 8+ 条正则参考

了解下面这些正则，你就理解了本工具 90% 的工作原理。

  1. 半角标点→全角（中文语境）： 遍历字符，若 ASCII 码在 0x21-0x7E 之间且前后有 CJK 字符，则加 0xFEE0 转为对应全角字符。这不是正则，而是字符码位运算，速度比正则更快。
  2. 全角标点→半角（英文语境）： 码位在 0xFF01-0xFF5E 之间的字符，减 0xFEE0 即得半角。
  3. 连续英文点→省略号： /\.{3,}/g 匹配 3 个及以上的英文点，统一替换为「…」（单省略号字符），后续再根据中文语境扩为「……」。
  4. 连续减号→破折号： /-{2,}/g 匹配 2 个及以上的半角减号，替换为「——」。
  5. 弯双引号→直角引号： 先定位所有的 " " "（U+201C U+201D U+0022），用栈结构判断嵌套层次，奇数层开「，偶数层（内层）开『，闭合时对称匹配。这种做法比简单的 replace 更准确。
  6. 弯单引号→直角引号： 同理处理 ' ' '（U+2018 U+2019 U+0027）。注意 U+2019 在英文里还常作撇号（don't），遇到英文撇号要特殊保留，所以需要判断两侧是否为英文字母。
  7. 零宽字符清理： /[\u200B-\u200D\uFEFF\u00AD\u2060]/g，覆盖零宽空格、零宽连字符、零宽断词符、BOM、软连字符、词接合符。
  8. 多余空白合并： /[ \t]+/g 合并连续空格和制表符为一个空格；/^\s+|\s+$/gm 去掉每行首尾空白（可配置）。
  9. NBSP 规范化： 把不间断空格 U+00A0 按上下文替换为普通空格或直接删除。中文语境下如果 NBSP 出现在两个汉字之间，通常是排版遗留，应删除；如果出现在中文和数字之间，可视情况保留为普通空格。

重要提示：CSV/TSV 数据不要盲目修标点

如果你的待处理文本是 CSV（逗号分隔值）或 TSV（制表符分隔值）格式的数据文件，请不要直接用默认模式处理。因为 CSV 里的半角逗号、半角双引号是结构性分隔符，一旦被替换成全角，整个数据文件就废了。正确做法是：先把 CSV 用 Excel 或脚本解析出每一列的非结构化文本列，单独复制出来用本工具处理，处理完再回填；或者选择「仅清理多余空白」模式，手动补全其他修正。

8. WebUtils 工具特点与隐私说明

纯本地处理，不上传不保留

本工具的所有文本处理逻辑——全半角转换、弯引号替换、省略号标准化、零宽字符清理——全部在你的浏览器内部完成。我们的服务器不会收到你粘贴的任何一个字符，甚至不会记录你曾经打开过本工具。原因很简单：工具页面是静态 HTML + JS 文件，打开后服务器和浏览器之间就没有通信了。你可以在浏览器开发者工具的 Network 面板里验证这一点：点击「一键校正」时，没有任何 XHR/Fetch 请求发出。

关标签页即回收内存

为了方便你中途离开后回来继续工作，本工具会把输入框的内容和当前选项保存到 localStorage（一个浏览器提供的本地键值数据库）里。这些数据只保存在你当前使用的这台电脑、这个浏览器的这个用户配置文件中，不会同步到云端。如果你对数据安全有更高要求，处理完敏感文本后可以：

  • 点击「清空」按钮——这会同时删除输入框内容、输出框内容和 localStorage 里的备份。
  • 关闭整个浏览器标签页或浏览器——内存中的数据会被操作系统立即回收。
  • 如果使用的是公共电脑，处理完后再清一次浏览器的 localStorage（Chrome/Edge 按 F12 → Application → Local Storage → 右键 Clear）。

对比需要上传文件的在线工具的风险

目前互联网上也有不少号称「在线标点修复」的工具，但其中相当一部分需要你把整篇文稿粘贴到网页里后，通过 AJAX 把内容发送到它们的服务器处理后再返回结果。对于日常闲聊的段子无伤大雅，但如果你的文稿包含：

  • 尚未发表的论文、书稿、专利草稿
  • 公司内部的产品需求文档、合同条款、财务数据
  • 个人的隐私信件、健康记录、法律文书

上传到他人服务器就等于把内容的控制权交了出去。你不知道对方会不会在后台把这些内容留存下来做语料训练、做搜索引擎索引、甚至直接售卖。本工具的纯前端实现从根本上杜绝了这一风险——你只需要相信你的浏览器，不需要相信我们。
